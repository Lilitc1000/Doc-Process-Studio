# 知识库语料说明与维护指南

本文面向后续接手本项目的开发者，说明事故报告生成所依赖的 RAGFlow 知识库中
各类语料的作用、它们如何参与生成、以及要继续完善时该怎么做。

---

## 1. 这套语料解决什么问题

事故报告正文由 LLM 生成。仅靠提示词约束时，模型容易出现两类问题：

1. **写得太空** —— 影响面没有量化、根因只有一句话、后续行动全是"加强监控"这类套话
2. **编造具体事实** —— 凭空写出设备名、时间戳、编号，看起来很像真事但无法核实

这套语料的定位是**补框架、不补事实**：为模型提供"这类事故的报告应该包含哪些要素、
根因该拆成几层、用词如何统一"的参照；而报告中的具体事实必须来自用户填写的表单。

一句话概括：**框架来自知识库，事实来自表单。**

生成链路中还有对应的护栏（事实边界声明、素材用途声明），与语料是配合关系——
语料负责提供"该写成什么样"，护栏负责防止"照抄语料里的事实"。两者都要保住。

---

## 2. 语料存放在哪里

**语料目前以文档形式存放在 RAGFlow 服务端，不在本代码仓库中。**

- 事故报告检索用的 dataset：`DAS事故报告`
- 历史样例存档 dataset（不参与检索）：`DAS历史报告存档`

连接信息（Base URL、API Key、参与检索的 dataset）由管理员在系统
**设置页**维护，保存在数据库中，无需改动代码。

要查看或导出现有语料，可通过 RAGFlow 的 HTTP API：

```bash
# 列出 dataset
curl -H "Authorization: Bearer <API_KEY>" \
  "<RAGFLOW_BASE_URL>/api/v1/datasets?page=1&page_size=100"

# 列出某个 dataset 下的文档
curl -H "Authorization: Bearer <API_KEY>" \
  "<RAGFLOW_BASE_URL>/api/v1/datasets/<DATASET_ID>/documents?page=1&page_size=100"
```

`<API_KEY>` 与 `<RAGFLOW_BASE_URL>` 从设置页获取（密钥不会明文回显）。

> **建议改进**：语料源文件目前没有纳入版本管理，修改无法追溯。
> 后续可考虑在仓库中建立 `docs/knowledge-base-corpus/` 目录存放语料源文件，
> 上传流程以该目录为准，这样语料的每次调整都能走 code review。

## 3. 语料分类（前缀规范）

每份语料的文件名以方括号前缀开头标明类型。这个前缀会出现在注入提示词的
`[RAGFlow · <来源>]` 标记中，直接告诉模型"这段素材是什么性质"。

| 前缀 | 作用 | 命名格式 |
|---|---|---|
| `[CHECKLIST]` | 要素清单：这类事故的报告必须交代哪些事实 | `[CHECKLIST] <domain>-incident.md` |
| `[MODE]` | 因果链模式：根因要拆成几个技术环节、如何递进 | `[MODE] <domain>-causal-chains.md` |
| `[ACTION]` | 处置动作库：后续行动可选用哪些具体动作 | `[ACTION] <domain>-remediation.md` |
| `[GLOSSARY]` | 术语词典：统一用词，替代口语化描述 | `[GLOSSARY] incident-terminology.md` |
| `[PATTERN]` | 写作范式：某一章节的写法与密度要求 | `[PATTERN] <topic>.md` |
| `[HISTORY]` | 历史样例：一篇完整报告作参照 | `[HISTORY] <编号>_<系统>_<YYYYMMDD>.md` |

`<domain>` 目前取 `database` / `network` / `storage`，与表单中的事故系统域对应。

### 各类语料的职责与写作要点

**`[CHECKLIST]` 要素清单**

定义一份报告必须尝试陈述的事实项。例如存储类事故要求交代阵列型号与容量、
故障盘位、降级持续时间、受影响的共享路径等。

写作要点：逐条列出要素名称 + 该要素要回答的问题；不要给出具体数值示例。

**`[MODE]` 因果链模式**

规定根因必须是**至少三个环节的技术链**，而不是一句话结论（如
"写延迟飙升 → WAL 同步积压 → 检查点无法推进"），每个环节都要有技术依据。

写作要点：给出链条的抽象形态与每环应包含的技术依据类型，用占位符示意，
不要写完整的具体故障案例。

**`[ACTION]` 处置动作库**

提供该领域可选的后续行动。这些是**候选动作**，模型应结合本次事故挑选，
而不是全部照抄。

写作要点：每条动作给出「动作 + 适用条件 + 预期效果」，并明确声明
"这是通用实践，不是某次事故的实际处置"。

**`[GLOSSARY]` 术语词典**

统一用词，收录操作员口语描述与规范术语的对应关系。

写作要点：三列对照（口语说法 / 规范术语 / 使用说明）。这是成本最低、
收益最快的完善点。

**`[PATTERN]` 写作范式**

针对特定章节给出写法与密度要求。目前有 impact-quantification，
规定影响面必须可量化、读者能据此重算出损失数字。

**`[HISTORY]` 历史样例**

一篇完整的真实报告，供人工参照结构、颗粒度与证据密度。

> **重要：`[HISTORY]` 不参与报告生成的检索。**
> 它单独存放在 `DAS历史报告存档` dataset 中。原因是历史样例通篇都是具体事实
> （设备、日期、编号），一旦被检索进提示词，会成为最强的"照抄"诱导源——
> 模型可能把样例中的日期、编号当作本次事故的事实写入报告。
> 设置页勾选检索 dataset 时，**不要勾选这个存档 dataset**。

## 4. 约束：框架语料不得包含具体事实

`[CHECKLIST]`、`[MODE]`、`[ACTION]`、`[GLOSSARY]`、`[PATTERN]` 这几类语料中，
**不得出现任何具体设备名、日期、数字、人名、版本号**。

举例也不行——类似 "for example NAS1 and NAS2" 的写法会让模型把示例
当作真实信息用于生成。需要举例时使用 `<device>`、`<count>` 这类占位符，
或明确标注 "example only / never reuse"。

**违反这条约束的表现**：生成的报告中出现与本次事故无关的机型、时间或编号。
排查时应首先回查语料内容，而不是调整提示词。

## 5. 语料如何参与生成

```text
语料文档 → 上传到 RAGFlow dataset → 服务端解析/切片
                                        ↓
表单填写 → 按事故域构造检索 query → 相似度检索 → 注入提示词 → LLM 生成
```

关键环节：

- **dataset 语言设置必须与语料正文语言一致**（当前为 English），
  否则解析与检索效果会下降
- **上传后确认解析状态**：文档状态应为 `run=DONE` 且 `chunk_count > 0`。
  停留在 `UNSTART` 的文档是静默失效的——不报错，但检索不到
- **参与检索的 dataset 在设置页勾选**（仅管理员可见），支持多选
- 检索 query 由表单的 `system` 字段映射到事故域，映射表见后端常量
  `INCIDENT_SYSTEM_DOMAIN_MAP`（位于 incident_report 模块的 constants 中）

### 检索参数

| 参数 | 配置位置 | 说明 |
|---|---|---|
| 参与检索的 dataset | 设置页勾选 | 更换连接后列表会重新拉取 |
| 相似度阈值 | 设置页 | 0.0 ~ 1.0，越高越严格 |
| topK | 设置页 | 单次注入的素材块上限 |
| 单文档片段上限 | 环境变量 `RAGFLOW_MAX_CHUNKS_PER_DOCUMENT` | 避免单篇长文档占满全部名额 |

前三项在设置页修改后立即生效，无需重启服务。

## 6. 如何继续完善

### 6.1 补齐缺失的领域语料

当前三个域的覆盖情况：

| 域 | CHECKLIST | MODE | ACTION |
|---|---|---|---|
| database | ✅ | ✅ | ✅ |
| storage | ✅ | ✅ | ✅ |
| **network** | ✅ | ✅ | ❌ **缺** |

优先补 `[ACTION] network-remediation.md`：参照 `[ACTION]` 的写作要点
（动作 + 适用条件 + 预期效果 + 声明不是某次事故的事实）。

### 6.2 新增写作范式（`[PATTERN]`）

可考虑补充：

- `[PATTERN] timeline-reconstruction` —— 时间线章节的写法（相对时间、证据来源标注）
- `[PATTERN] root-cause-narrative` —— 根因叙述的组织顺序

### 6.3 增加历史样例

放入 `DAS历史报告存档`，命名保持 `[HISTORY] <编号>_<系统>_<YYYYMMDD>.md`。
样例质量比数量重要：一篇结构完整、证据充分的报告胜过五篇流水账。

### 6.4 扩充术语词典

遇到操作员口语与规范用词对不上的情况，向 `[GLOSSARY]` 增加对照行。

## 7. 改完怎么验证

建议按以下顺序，全部使用系统自身或 RAGFlow 的能力，不依赖额外脚本：

1. **确认解析状态** —— 在 RAGFlow 中查看刚上传/更新的文档，
   状态应为 `DONE` 且切片数大于 0
2. **用 RAGFlow 的检索测试** —— 输入与目标事故域相关的 query，检查：
   - 目标语料是否被召回（排在前列）
   - 召回内容是**框架**（要素、模式、动作）而不是某个具体事故的事实
   - 换成其他域的 query 时，不会召回明显无关的素材
3. **在系统中生成一份报告** —— 观察三个信号：
   - 要素是否齐全（对应 `[CHECKLIST]` 是否生效）
   - 根因是否为多环节链条而非一句话（对应 `[MODE]` 是否生效）
   - 是否出现凭空的具体设备/日期（对应第 4 节的约束是否被破坏）
4. **确认设置页勾选正确** —— 特别是没有把 `DAS历史报告存档` 勾进检索 dataset

出现问题时优先回查语料内容与 dataset 勾选，其次再考虑调整相似度阈值或 topK。

## 8. 常见问题排查

| 现象 | 可能原因 |
|---|---|
| 生成结果要素缺失 | 对应域的 `[CHECKLIST]` 未上传，或解析未完成（`run != DONE`） |
| 根因仍是一句话 | `[MODE]` 未被召回；检查相似度阈值是否过高、dataset 是否勾选 |
| 出现编造的设备 / 日期 | 框架语料混入了具体事实，或 `[HISTORY]` 存档被误选进检索 dataset |
| 后续行动全是套话 | 对应域缺少 `[ACTION]` 语料（network 目前就缺） |
| 设置页知识库列表为空 | 当前凭据下无可访问 dataset，或连接不可用（可用"测试连接"验证） |
| 改了语料但生成结果没变化 | 文档解析未完成，或设置页勾选的 dataset 不是刚更新的那个 |
